# StorageBackend interface contract

`StorageBackend` (local filesystem + S3-compatible in v1, per decision #5) exposes `store(String key, InputStream content, long contentLength, String contentType) → String reference`, `retrieve(String reference) → InputStream`, `delete(String reference)`, and `exists(String reference)`, with a single unchecked `StorageException` base plus a `StorageObjectNotFoundException` subtype. Content flows as `InputStream` in both directions (never `byte[]`, never Spring's `Resource`) so large files never fully materialize in heap and the contract stays framework-neutral; `contentLength` is passed explicitly because S3's single-shot `PutObject` needs a known `Content-Length` up front. The returned `reference` is a single opaque `String` — not a discriminated/multi-field type — persisted as-is on the File entity's `storageReference` column; core never interprets it, only round-trips it, so each backend is free to encode its own format (local: relative path; S3: bucket-qualified key) without a shared schema.

The active backend is chosen via `file-manager.storage.backend=local|s3`, but `file-manager-spring-boot-autoconfigure` never compiles against a concrete backend: each storage module (`file-manager-storage-local`, `file-manager-storage-s3`) ships its own `@ConditionalOnProperty`-guarded `@AutoConfiguration`, self-registered via `AutoConfiguration.imports`. A consumer depends only on the storage module(s) it actually uses — e.g. adding `file-manager-storage-local` pulls in zero AWS SDK — mirroring how Hibernate dialects are selected by property without forcing unused JDBC drivers onto the classpath. Only one backend is active per deployment in v1; no per-Folder/per-File backend selection.

AWS SDK v2's `S3Client` was confirmed to work fully against MinIO (via `endpointOverride` + `forcePathStyle(true)`) for all four operations this contract needs, so "S3-compatible" (decision #5) already covers MinIO without a separate implementation or naming change.

## Considered options

- **Rich `StorageReference` type** (discriminated union per backend, e.g. `{bucket, key}` vs `{path}`) instead of an opaque `String` — rejected: core never branches on the reference's shape, only stores and echoes it back, so the extra mapping/serialization machinery buys nothing.
- **`org.springframework.core.io.Resource`** instead of `InputStream` for content — rejected: `file-manager-core` already depends on Spring Data JPA (decision #12) but is otherwise meant to stay framework-neutral; `Resource` would leak further Spring surface into a domain contract for no gain over plain `InputStream`.
- **Centralized backend instantiation in `file-manager-spring-boot-autoconfigure`** (an if/else on the property, compiled against both storage modules) — rejected: it would force every consumer's classpath to carry both backends' dependencies (including the AWS SDK) regardless of which one they use.
